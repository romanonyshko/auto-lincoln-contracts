# @auto-lincoln/contracts

Shared contracts (schemas and types) for the Auto Lincoln project. Both the backend and the frontend use them, so request/response formats stay identical.

Schemas are written with [Zod](https://zod.dev), and TypeScript types are inferred from them with `z.infer`.

## Structure

```
auth/       — login (LoginRequest, LoginResponse)
catalogue/  — catalogue lookups for the cascading filters
  categories.ts — Category, CategoriesResponse
  carmakers.ts  — Carmaker, CarmakersResponse
  car-models.ts — CarModel, CarModelsResponse
  engines.ts    — Engine, EnginesResponse
chat/       — support chat WebSocket events (ChatMessage, ClientChatEvent, ServerChatEvent)
common/     — shared schemas and constants
  api.ts        — API prefix, REST routes (API_ROUTES), WS routes (WS_ROUTES), auth cookie name
  errors.ts     — API error format (ApiError)
  pagination.ts — paginated(itemSchema) → { items, nextCursor }
  types.ts      — Id (uuid), IdParams ({ id } in route params), Timestamps (createdAt / updatedAt)
dashboard/  — GET /api/dashboard response (DashboardResponse)
parts/      — parts
  part.ts       — Part, Currency
  get-parts.ts  — PartsQuery, PartsResponse
users/      — user contracts
index.ts    — entry point, re-exports all contracts
```

## Install and build

```bash
npm install
npm run build
```

The build runs `tsc` into `dist/` (JS + `.d.ts` + source maps). `dist/` is not committed — it is generated by the build.

## Usage

```ts
import {
  LoginRequestSchema,
  type LoginRequest,
  API_PREFIX,
  API_ROUTES,
} from "@auto-lincoln/contracts";

const body: LoginRequest = LoginRequestSchema.parse(req.body);
const url = `${API_PREFIX}${API_ROUTES.auth.login}`;
```

## Catalogue

Data for the `/parts/catalogue` page: the category grid and the cascading Carmaker → Model → Engine filters. The lookups are flat lists linked by parent id (`CarModel.carmakerId`, `Engine.modelId`).

| Route | `API_ROUTES` | Response |
| --- | --- | --- |
| `GET /api/categories` | `categories` | `CategoriesResponse` — `Category[]` |
| `GET /api/carmakers` | `carmakers` | `CarmakersResponse` — `Carmaker[]` |
| `GET /api/carmakers/:id/models` | `carmakerModels(id)` | `CarModelsResponse` — `CarModel[]` |
| `GET /api/models/:id/engines` | `modelEngines(id)` | `EnginesResponse` — `Engine[]` |
| `GET /api/parts` | `parts` | `PartsResponse` — `{ items: Part[], nextCursor: string \| null }` |

Routes with a parameter are functions: on the web, `API_ROUTES.carmakerModels(id)`. In Nest the controller prefix comes from the contract and the rest goes into the decorator:

```ts
@Controller(API_ROUTES.carmakers)   // '/carmakers'
@Get(':id/models')
```

The engines controller uses `API_ROUTES.models` (`/models`) as its prefix.

- `:id` is validated with `IdParamsSchema`: not a uuid → 400, a valid uuid with no record → 404, a parent with no children → 200 `[]`.
- `Category.image` is a relative path to an image in the web app (`/categories/*.jpg`), not a URL.
- `Part.price` is a `number` (`Decimal(10, 2)` in the DB; the backend converts it with `toNumber()`). `Part.image` is `string | null`. `compatibleEngineIds` is an array of engine ids (a many-to-many relation in the DB).

### `GET /api/parts` query — `PartsQuerySchema`

| Param | Type | What it does |
| --- | --- | --- |
| `category` | uuid, optional | filter by category |
| `make`, `model`, `engine` | uuid, optional | filter by id at any selection depth |
| `search` | string, optional | `trim`; empty or whitespace-only → `undefined` (ignored) |
| `cursor` | uuid, optional | id of the last part on the previous page |
| `limit` | integer 1–100, default 20 | `z.coerce` — query values arrive as strings |

`PartsQuery` (`z.infer`) is the type after `parse`; the backend uses it. The schema's input and output differ (`limit` is a string or missing on input), so the web needs `z.input<typeof PartsQuerySchema>` to build URLs.

`nextCursor: null` means the last page.

## WebSocket chat

The path is `WS_ROUTES.chat` (`/ws/chat`). It is separate from `API_ROUTES` because `API_PREFIX` is not added to it. Messages are JSON, a discriminated union on the `type` field.

| Direction | Schema | Events |
| --- | --- | --- |
| client → server | `ClientChatEventSchema` | `{ type: 'message:send', clientId, text }` — `clientId` is a client-generated uuid, `text` is 1–1000 characters after `trim` |
| server → client | `ServerChatEventSchema` | `{ type: 'message:new', message: ChatMessage }`, `{ type: 'error', code: 'INVALID_JSON' \| 'VALIDATION_ERROR', clientId?, message }` |

`ChatMessage` is `{ id, clientId?, author: 'user' | 'support', text, sentAt }`. The server sets `id` and `sentAt`. `clientId` is present only in the reply to a client message; the server greeting has none.

In an `error` event, `clientId` tells which client message failed validation. It is present only when the server could read it (a valid uuid). It is never present for `INVALID_JSON`.

Incoming data is validated with the schema (`ClientChatEventSchema.safeParse(data)`), not the type: the `ClientChatEvent` type disappears after compilation.

How the server behaves (close codes, greeting) is described in `auto-lincoln-api-nest/README.md`.

## Adding a new contract

1. Create a file in the matching folder (for example, `parts/update-stock.ts`).
2. Write the Zod schema and infer the type from it with `z.infer`.
3. Add a re-export to `index.ts` (with the `.js` extension, because the project uses `nodenext`).
4. Run `npm run build`.
